# Project Valhalla value classes support

* **Type**: Design proposal
* **Author**: Evgeniy Zhelenskiy
* **Status**: Proposed
* **Discussion and feedback**: [GitHub](https://github.com/Kotlin/KEEP/discussions/510)
* **Related YouTrack issues**: [KT-84904](https://youtrack.jetbrains.com/issue/KT-84904), [KT-87569](https://youtrack.jetbrains.com/issue/KT-87569)

# Abstract

This KEEP describes experimental support for compiling Kotlin value classes to
[Project Valhalla](https://openjdk.org/projects/valhalla/) value classes on the JVM, as specified by
[JEP 401: Value Classes and Objects](https://openjdk.org/jeps/401).

Kotlin already unboxes inline value classes where it can, but only in a limited set of situations, and every
class it compiles — including value classes — is still an ordinary JVM identity class at run time. With this
support, Kotlin value classes are instead compiled as Project Valhalla value classes, so that their instances
behave as value objects and can be optimized by the JVM in many more cases than Kotlin can achieve on its own.

The support is gated behind a new compiler flag, `-Xvalhalla-value-classes`, and behind the JVM preview
machinery on both the compiler and the runtime. Interoperability with Java value classes and with the value
classes of the JDK is supported as well, and only needs the JVM preview machinery.

This is an **experimental** feature intended for trying Project Valhalla out with Kotlin; it is not meant for
production use, and its shape may change as JEP 401 evolves toward integration into a mainline JDK.

# Overview

Project Valhalla value classes and their semantics are specified by [JEP 401](https://openjdk.org/jeps/401);
the value classes Kotlin can express are covered by
[KEEP-0454](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0454-better-immutability-value-classes-MFVC.md)
(full value classes) and
[KEEP-0468](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0468-inline-value-classes.md)
(inline value classes). This proposal only concerns compiling such declarations to JEP 401 value classes on a
Valhalla-capable JVM, so that their instances behave as value objects at run time.

## What this feature does

When enabled, the compiler compiles every Kotlin value class as a JEP 401 value class rather than as an
ordinary identity class. Concretely, for each such declaration the compiler:

- emits a class file without the identity marker (the `ACC_IDENTITY` access flag), which is how the JVM
  recognizes a value class and reports `Class.isValue() == true`;
- marks the class's instance fields *strict* (they must be assigned before the superclass initializer runs).

Declarations that are *not* value classes keep the ordinary identity representation (`ACC_IDENTITY` set,
non-strict fields), exactly as Kotlin compiles them today.

Whenever the JVM target supports Project Valhalla, the compiler also records the JEP 401 `LoadableDescriptors`
attribute for the value class types used in field and method signatures, so the JVM can preload and flatten
them, and keeps the attribute correct even when class files are regenerated (for example, when the body of an
inline function is re-emitted at a cross-module call site). Kotlin and Java value classes interoperate in both
directions.

## Experimental status

Project Valhalla value classes are a *preview* feature of the JVM, and Kotlin's support for them is
correspondingly **experimental**:

- It exists only to let people try Project Valhalla out with Kotlin and to co-evolve with JEP 401. It is not
  supported for production, and the flag and the generated bytecode may change.
- It requires the JVM preview machinery to be explicitly enabled, at both compile time and run time (see
  [Preview requirements](#preview-requirements)).
- It requires a Valhalla-capable JDK.

## Getting a Valhalla-capable JDK

A JDK that implements JEP 401 is published as **Project Valhalla Early-Access builds** at
[https://jdk.java.net/valhalla/](https://jdk.java.net/valhalla/): download an early-access JDK, unpack it, and
point the compiler and the runtime at it. At the time of writing these builds implement
*JEP 401: Value Classes and Objects (Preview)* on top of JDK 28, corresponding to JVM target 28. Because preview
class files are tied to the exact JDK feature version that produced them, the compile-time JVM target must
match the Valhalla JDK used to run the result.

# How to use

## The `-Xvalhalla-value-classes` flag

Valhalla value classes are enabled with a single JVM compiler flag:

```
-Xvalhalla-value-classes
```

It is off by default. When it is on, every Kotlin value class is compiled to and behaves as a Project Valhalla
value class (see [Valhalla value classes](#valhalla-value-classes)).

## Preview requirements

Because JEP 401 is a JVM preview feature:

- **At compile time**, `-Xvalhalla-value-classes` requires JVM target 28 or later and Kotlin's JVM preview flag,
  `-Xjvm-enable-preview`; the compiler reports an error otherwise.
- **At run time**, the produced class files are preview class files, so running them requires the standard
  `--enable-preview` flag on a Valhalla-capable JDK of the matching feature version. Running them on a
  non-preview or non-Valhalla JVM will be rejected by the class loader.

## Levels of support

What the compiler does depends on the JVM target, the preview flag, and `-Xvalhalla-value-classes`.

### No Valhalla support (default)

Without JVM target 28 or `-Xjvm-enable-preview`, the target JDK is *not* Valhalla-compatible: no declaration is
compiled as a Valhalla value class, and the compiler emits regular JVM bytecode. Every class — including value
classes — keeps its identity: the identity marker stays set and instance fields are non-strict. This is the
representation Kotlin has always produced, and it requires neither the preview flags nor a Valhalla JDK.

### Valhalla JVM target without the flag

With JVM target 28 or later and `-Xjvm-enable-preview`, but without `-Xvalhalla-value-classes`, **no**
Kotlin class changes representation. A full value class, an inline value class, a value object, a
`@JvmRecord value class`, and abstract or sealed value classes all keep the ordinary identity representation —
none of them becomes a value class, and no instance field is strict:

```kotlin
value class Point(val x: Int, val y: Int)      // still an identity class
inline value class Id(val value: Int)          // still an identity class
```

What changes is the treatment of the value classes of the platform:

- the [JDK value classes](#loadabledescriptors-for-jdk-value-classes-and-willbecomevalue) (`java.lang.Integer`,
  `java.time.LocalDate`, `java.util.Optional`, …) and [Java value classes](#interoperability-with-java-value-classes)
  are treated as value classes;
- the `LoadableDescriptors` attribute is emitted for them.

For a user, this mostly changes **how primitives behave**. On a Valhalla JDK the primitive wrapper types
(`java.lang.Integer` and friends) are value classes, so a *boxed* primitive no longer has reliable identity,
and code that relies on the identity of boxed primitives behaves differently. For example:

```kotlin
fun check(): String {
    val a = 1000
    val b = 1000
    // '===' is not allowed directly on Int, but after boxing to Any it compares references:
    val boxA: Any = a
    val boxB: Any = b
    // On an ordinary JDK these are two distinct Integer objects (outside the -128..127 cache),
    // so the boxes are not identical. On a Valhalla JDK Integer is a value class with no identity,
    // so '===' compares by value and this assertion no longer holds.
    if (boxA === boxB) return "Fail: boxes are identical"
    return "OK"
}
```

### Valhalla value classes

With `-Xvalhalla-value-classes` in addition, every Kotlin value class is compiled as a Valhalla value class:

- full value classes, introduced in
  [KEEP-0454](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0454-better-immutability-value-classes-MFVC.md),
  including value objects and abstract and sealed value classes;
- inline value classes (`inline value class` or `@JvmInline value class`, see
  [KEEP-0468](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0468-inline-value-classes.md));
- `@JvmRecord value class`es, which become value records.

The only exception is a value class extending a value class compiled as an identity class (see
[Value classes extending identity-compiled value classes](#value-classes-extending-identity-compiled-value-classes)).

```kotlin
value class Point(val x: Int, val y: Int)   // a Valhalla value class — no identity, strict fields
inline value class Id(val value: Int)       // a Valhalla value class too
```

This is the mode to use to **try Project Valhalla out with Kotlin**: all Kotlin value classes run as value
objects and can benefit from flattening and scalarization.

For inline value classes, this also changes their **boxes**. An inline value class has a boxed reference form,
which, as an identity class, has JVM identity. Kotlin forbids relying on it — you cannot use `===`
(or `System.identityHashCode`, or synchronization) on an inline value class value directly — but it is
*discoverable through workarounds*, namely by upcasting to `Any` first. With Valhalla value classes, the boxes
have no identity, and such code observes value semantics instead:

```kotlin
inline value class Id(val value: Int)

fun check(): String {
    val id = Id(1)
    // id === id                 // forbidden by the compiler: '===' on a value class
    val boxA: Any = id           // boxing produces a box
    val boxB: Any = id           // a second boxing produces another box
    // Without Valhalla value classes, these are two distinct boxes; with them, '===' compares by value.
    if (boxA !== boxB) return "Fail: boxes differ"
    return "OK"
}
```

A Kotlin value class is seen by Java as a value class:

```kotlin
// Kotlin
value class Point(val x: Int, val y: Int)
```

```java
// Java
Point p = new Point(1, 2);
boolean isValue = Point.class.isValue();   // true
```

# What the support includes

## Marking value classes and identity classes

The core of the feature is deciding which declarations are Valhalla value classes and emitting the corresponding
class files:

- **Value classes** are emitted without the identity marker (`ACC_IDENTITY` cleared), which is how the JVM
  recognizes them (`Class.isValue()` becomes `true`), and their instance fields are marked `strict`.
- **Identity classes** — ordinary classes, and all Kotlin classes without `-Xvalhalla-value-classes` — keep
  `ACC_IDENTITY` and non-strict fields, i.e. exactly the representation Kotlin emits today. Marking a class as
  *not* a value class is as much a part of the support as marking one as a value class.
- **Abstract and sealed value class hierarchies** are supported: an abstract value class compiles to an
  abstract value class, and a sealed value class keeps its `permittedSubclasses`, so
  `Class.isSealed`/`permittedSubclasses` reflection continues to work.

## Value classes extending identity-compiled value classes

A Kotlin value class compiled without `-Xvalhalla-value-classes` is an identity class in its class file, and a
Valhalla value class cannot extend an identity class. So when a value class extends such a value class from a
library, it is compiled as an identity class, too, and the compiler reports a warning:

```kotlin
// library, compiled without -Xvalhalla-value-classes
abstract value class Shape {
    abstract val area: Double
}

// application, compiled with -Xvalhalla-value-classes
value class Square(val side: Double) : Shape() { // Warning: 'Square' is compiled as an identity class, too
    override val area: Double get() = side * side
}
```

The class becomes a Valhalla value class once its superclass is recompiled with `-Xvalhalla-value-classes`.
The same applies transitively to value classes extending such classes from the same module.

## Interoperability with Java value classes

The support wires value-ness through the whole Java-interop surface so that Kotlin and Java value classes are
mutually usable:

- Java `value class`/`value record` declarations are recognized as value classes when read from source and
  from class files compiled for JVM 28 or later with preview features, also without `-Xvalhalla-value-classes`.
  A Java value class is usable from Kotlin as an ordinary type, and the compiler treats it as a value class,
  including listing it in `LoadableDescriptors` when it appears in a signature:

  ```java
  // Java
  public value record Complex(double re, double im) {}
  ```

  ```kotlin
  // Kotlin
  fun magnitudeSquared(c: Complex): Double = c.re() * c.re() + c.im() * c.im()
  ```

- Kotlin value classes are exposed to Java as value classes (`Class.isValue()`) with
  `-Xvalhalla-value-classes`, across module boundaries.
- Reflection agrees with the class file: `kotlin.reflect.KClass.isValue` reports `true` for Java value classes,
  and their members are callable through Kotlin reflection (`KFunction.call`/`callBy`).

## The `LoadableDescriptors` attribute

For the JVM to preload and flatten a value-typed field or parameter, the class that uses the type must advertise
it in the JEP 401 `LoadableDescriptors` attribute. Whenever the JVM target is 28 or later with preview features,
the compiler emits this attribute — matching javac's behavior — listing the descriptors of the value class types
used in field types and in method parameter and return types. The attribute:

- is emitted on regular (identity) classes, on value classes, and on the file class that holds a static
  value-typed field;
- lists Kotlin value classes compiled as Valhalla value classes, Java value classes, and the JDK value classes
  (boxed primitives, `LocalDate`, `Optional`, …), but not identity reference types such as `String`, nor abstract
  or sealed value classes such as `Number` (only concrete value classes can be flattened), nor bare primitives
  (`int`);
- lists the underlying type for a property of an inline value class type, since it is compiled to that type;
- leaves out the class's own type when a value class has a field of its own type (the class is already being
  loaded), while the class's other value-typed fields are still listed; and when two value classes each hold a
  field of the other's type, each one lists the other. Both rules match javac.

## `LoadableDescriptors` for JDK value classes and `@WillBecomeValue`

A number of JDK classes (`Integer`, `Optional`, `LocalDate`, …) are value classes in the Valhalla preview JDK.
The compiler lists such types in the `LoadableDescriptors` attribute of the classes that use them. This choice
is deliberate:

- **It matches javac.** javac emits the same attribute for the same field types, so the bytecode Kotlin
  produces is consistent with the platform's.
- **It produces more efficient code.** Listing a value class in `LoadableDescriptors` is the preload hint the
  JVM needs to flatten and scalarize fields of that type.
- **It works without recompiling the stdlib.** On a JDK that actually ships value-class versions of these
  stdlib types, the preload hint lets them be treated as value classes at load time — Kotlin does not need to
  recompile against, or re-mark, a value-class stdlib to get the benefit.

The same mechanism applies to Kotlin's own analogue of value-based classes, the
[`@WillBecomeValue`](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0470-will-become-value.md)
annotation: classes marked as *will become value* are listed in the `LoadableDescriptors` attribute of their
users, so that they, too, gain the preload/flattening benefit ahead of an actual migration to `value class` and
without forcing a recompilation of their dependencies. Kotlin value classes compiled as identity classes because
of [their superclass](#value-classes-extending-identity-compiled-value-classes) are listed for the same reason.
